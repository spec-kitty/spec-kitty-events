# Status-transition parity corpus

Each JSON document in `cases/` is one language-neutral `(prior log, tasks files,
request) -> expected outcome` case. The file stem equals its kebab-case `id`.
`oracle: core` documents are generated by running core at
`512567eee71e31bb39f580c4f7acf8b865e9d1b2`; hand-written documents are
`oracle: protocol` only. The package never imports core.

## Fields and consumers

- `layer`: `domain` is judged by the write authority alone, `edge` by
  `WriteBodies`, and `service` by replay, fold, persistence and acknowledgement
  handling over HTTP.
- `area`: `lane_machine`, `guard`, `force`, `done_evidence`, `force_note`,
  `stale`, `unknown_lane`, `dependency`, `claim`, `review_claim`,
  `start_rejected`, `batch`, `annotation`, `fold`, `replay`, or `alias`.
- WP06 consumes domain cases except `dependency`, `claim`, `review_claim`,
  `start_rejected`, and `batch`, which WP07 owns. WP08 consumes `edge` and
  `service` cases.
- `operation`: `transition`, `start_implementation`, `start_review`, or
  `annotation`. `mission` fixes the directory, ULID and slug; `log` contains
  prior JSON values in file order. `log_text` replaces it where blank lines,
  CRLF or malformed input must be represented. `tasks` maps filenames below
  `tasks/` to complete Markdown text.
- `request.kind` is `unit`, `batch`, or `annotation`; each unit carries `wpId`,
  an optional operation, an optional `implementationEvidencePresent` (boolean or
  null; a transition unit's request-only evidence flag, never part of its rows),
  and ordered rows. `checkout_append`, `checkout: "."`,
  and the Mission directory are implied by the corpus.
- `expected` is an acknowledgement with per-unit replay/append counts and
  optional `fsyncs`, or a refusal with its contract code, nullable reason URN,
  nullable message, and nullable zero-based unit index. Core refusal messages
  are verbatim exception strings. The events-side `stale_from_lane` reason has
  no core equivalent and appears on protocol stale-from-lane refusals.
- `core_call` records the core entry point and keyword arguments used for a
  generated case. `notes` explains the scenario or names the protocol spec row.

Timestamps use the shared Python/Java ISO-8601 subset: UTC `+00:00`, seconds
precision, and no fractional or named zones (ruling R12).

## Start from `planned`

The one-to-two exception is `start_implementation` on a `planned` work package
(ruling R13). One core call appends `planned -> claimed` and
`claimed -> in_progress`; the case records a two-unit batch whose units both
have `operation: start_implementation`. Every other case maps one core call to
one unit.

## Regeneration and drift

Run with core's locked interpreter from the pinned core checkout and with
`SPEC_KITTY_CORE_CHECKOUT` naming that checkout. The generator reads the required
`major.minor` from that checkout's `.python-version` and exits 2 on an interpreter
mismatch. The supplied WP04 environment uses core's Python **3.11.15**:

```sh
CORE=/path/to/core-pin
SPEC_KITTY_CORE_CHECKOUT="$CORE" "$CORE/.venv/bin/python" \
  scripts/conformance/generate_transition_parity.py
SPEC_KITTY_CORE_CHECKOUT="$CORE" "$CORE/.venv/bin/python" \
  scripts/conformance/generate_transition_parity.py --check
```

Generation initializes a fresh temporary git repository per case, writes the
Mission metadata and tasks, uses core calls to build prior logs, then calls the
operation's real core entry point. Caller-supplied core arguments are restricted
to fields present in the request rows; all other guard inputs are core-derived.
It stops batches at their first refusal. `--check` writes nothing, reports
differing core ids (including deleted intents), and exits nonzero on drift.
Generation also renders two families of protocol cases: the stale-from-lane refusal overlay,
adding the events-side `stale_from_lane` expectation under research §11 decision 17, and the
frontmatter-fact refusals (R15, R19-R29), which reuse a core case's request and log with the
service's refusal as the expectation. Core's behaviour on those inputs is an accident of its
stack (research §11 decision 19), so they are `oracle: protocol`, never core parity. Every other
protocol case is left untouched.

`unreachable.json` maps a wholly unreachable reason URN to its proven cause. Its
`partial` object records an unreachable half of a reason that remains reachable
through another half. Every other reason has a committed refusal case.
