# 2026-10-31 — service-v0.1.0-rc.1: the first events service release

**Service line, first pre-release** · package unchanged (`11.3.0`) ·
[ADR-0003](../adr/0003-gradle-build-and-service-release-line.md) ·
[ADR-0004](../adr/0004-dual-artifact-line.md)

The operator approved `service-v0.1.0-rc.1` on 2026-10-31 (rulings on
[spec-kitty/spec-kitty#6117](https://github.com/spec-kitty/spec-kitty/issues/6117#issuecomment-6544221340)),
as ADR-0003 requires for the first `service-v0.x` tag. The operator pushes the tag on a
commit of `main`. `service-release.yml` then builds, checks, attests and publishes the
release as a GitHub pre-release, never marked latest. Nothing reaches PyPI: the package
line (`v*`) is separate and stays at `11.3.0`, the version this release is built and
tested against.

## What the release publishes

`<ver>` is `0.1.0-rc.1`. The asset set is the
[ADR-0003 asset table](../adr/0003-gradle-build-and-service-release-line.md#release-assets),
exactly. `scripts/release/service-release-assets.sh` refuses a set with anything missing
or extra.

| Asset | What it is |
|---|---|
| `mission-status-api-0.1.0-rc.1-linux-x64` | Mission Status Read API, GraalVM native, Linux x86-64 |
| `mission-status-api-0.1.0-rc.1-linux-arm64` | the same, Linux ARM64 |
| `mission-status-api-0.1.0-rc.1-macos-arm64` | the same, macOS on Apple silicon |
| `mission-status-api-0.1.0-rc.1-windows-x64.exe` | the same, Windows x86-64 |
| `mission-status-api-0.1.0-rc.1.jar` | Spring Boot executable jar, the JVM fallback (needs Java 25 or newer) |
| `contract-bundles-0.1.0-rc.1.tar.gz` | `bundle/mission-status/openapi.yaml` and `bundle/mission-write/openapi.yaml` |
| `contract-tools-0.1.0-rc.1.tar.gz` | `contracts/tools/*.py`, `pins.json`, `enum_pins.json` |
| `conformance-fixtures-0.1.0-rc.1.tar.gz` | the service conformance fixtures, golden requests, leak patterns and torn-tail cases |
| `<asset>.sha256` | one per asset above |
| `SHA256SUMS` | every asset above, sorted by name |

That makes 8 assets, 8 `.sha256` files and `SHA256SUMS`: 17 files. Each of the 8 assets has
a build-provenance attestation.

### Native or jar, per platform

| Platform | What runs |
|---|---|
| Linux x86-64 | native |
| Linux ARM64 | native |
| macOS on Apple silicon | native |
| Windows x86-64 | native (`.exe`) |
| macOS on Intel, Windows ARM64, any other platform | no native build: the jar, on Java 25 or newer |

The binaries are unsigned, so macOS Gatekeeper and Windows SmartScreen warn on first run.

The write service (`command-cli`) is not in this release. It joins the line in a later
release under its own asset names (`command-cli-<ver>-<target>[.exe]`,
`command-cli-<ver>.jar`).

## How to verify a download

```bash
sha256sum --check --strict SHA256SUMS
gh attestation verify <asset> --repo spec-kitty/spec-kitty-events \
  --signer-workflow spec-kitty/spec-kitty-events/.github/workflows/service-release.yml \
  --source-ref refs/tags/service-v0.1.0-rc.1
```

Core pins the release with
`spec-kitty service vendor --service read-service --tag service-v0.1.0-rc.1`. That command
resolves the tag to its commit, downloads `SHA256SUMS`, maps the 8 assets onto the pin by
name, checks each download against its line and writes `pins/read-service.source.yaml`.
[Service protocol and releases](../guides/service-protocol-and-releases.md#cut-a-release)
describes the release steps.
