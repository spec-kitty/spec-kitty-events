section: Breaking
---

- `validate_transition()` and `reduce_status_events()` now admit exactly core's unforced edge graph (`wp_state.py` at spec-kitty `512567ee`) plus `None -> planned`, in a minor release, `11.5.0` (#237; #231 item 4.6; ruling D4). Unforced edges removed: `for_review -> approved`, `for_review -> done`, `for_review -> in_progress`, `for_review -> planned`, `in_review -> for_review`, `genesis -> blocked` and `blocked -> blocked`. Producers must force those moves with a reason (and a `review_ref` where required), as core does. Force semantics and guards are unchanged. The fixtures `wp-status-changed-unforced-for-review-to-in-progress-with-review-ref-valid` and `lifecycle-wp-status-changed-summary-done-valid` are now forced events (their unforced forms are new invalid fixtures), and `zeitgeist_attrs/valid/wp_status_changed_done_drops_evidence.json` is rerouted from `for_review` to `in_review` in `payload.from_lane` and `expected_attrs.from_lane` (same id, still valid and unforced; Zeitgeist consumers' golden `expected_attrs` change). Three packaged fixtures changed in all. The package docstring now lists `spec_kitty_events.status_log` (#231 item 4.3).

  This narrows the accept/reject boundary (`contracts/versioning-and-compatibility.md` classifies that as breaking); it ships as a minor by ruling D4 (maintainer, 2026-11-09; operator DM-01M758AR, "Full D4"), a recorded exception, because the package mirrors core's write authority. Consequences for consumers: `spec_kitty_events.conformance.validate_event("WPStatusChanged", ...)` now rejects these unforced moves; `reduce_lifecycle_events` (which delegates to `reduce_status_events`) is affected too; historical append-only logs that already hold such unforced moves now reduce differently in `reduce_status_events` (the event becomes a `TransitionAnomaly` and the WP keeps its earlier lane), while `diary.reduce` / `spec_kitty_events.status.reduce`, the reducer core uses, applies no edge check and is unchanged, so the two package reducers can disagree on such history (`force=True` applies to new events only; existing history cannot be rewritten). Whether spec-kitty-saas ingress validates with `validate_event` or reduces with `reduce_status_events` is not verifiable from this repo: consumers must pin `11.5.0` deliberately, and the central CLI-SaaS contract must record the narrowed acceptance (follow-up: #258).
